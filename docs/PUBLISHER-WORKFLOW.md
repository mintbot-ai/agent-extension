# Local publisher workflow

`axp` prepares files locally. **Init, check, pack, sign and release never upload,
install dependencies, run a build command, execute package hooks, or contact a
registry.** `resolve` is the separate, explicitly networked host-preview command.
No manifest/schema fields were added for these tools.

## Start with a runnable example

```sh
axp init --template skill --publisher extensions.your-domain.com \
  --name hello --description "A greeting skill" --dir hello
cd hello
axp validate agent-extension.json
axp check                         # exit 1: an honest draft, not a release
```

Use a DNS name you control. `--template` accepts:

| Template | Example component | Run it explicitly |
| --- | --- | --- |
| `skill` | `provides.skills`, `payload/SKILL.md` | Read the greeting instructions |
| `cli` | `provides.tools`, Python greeting command | `python3 payload/main.py Alice` |
| `mcp` | `provides.mcp_servers`, stdio JSON-RPC greeting tool | `python3 payload/main.py` with an MCP stdio client |
| `service` | `provides.services`, loopback HTTP health endpoint | `python3 payload/main.py --port 8765` |

Every example includes `install.sh`, `uninstall.sh`, `healthcheck.sh`, a Python
lifecycle helper, a README, component files, a manifest and `axp.toml`. Python 3
and a POSIX shell are required. The default target is `posix`; `--runtime` still
selects target declarations, not host-specific adapters or registration logic.
Run and test adapters yourself before claiming support for another runtime.

Explicitly run `sh install.sh` to copy the payload to
`~/.local/share/axp/<name>/payload`; set `AXP_PREFIX` to change the prefix. Install
and uninstall are idempotent. Uninstall removes only example payload files and
preserves state and unrelated files. Lifecycle operations preflight all destinations:
symlink files/directories (including prefix ancestors), hardlinked files and
non-file destinations are refused before changing payload files. Health checks **installed files**, not a
running process. Service examples run in the foreground, bind only loopback,
and are neither started by install nor registered as a system service. MCP is
a minimal stdio example, not a general-purpose MCP framework.

Without `--template`, `init` keeps its legacy manifest-only behavior. Template
creation preflights every destination and refuses collisions unless `--force`
is explicit. Even with `--force`, symlink destinations, hardlinked files and non-file collisions
are refused. No keys are generated by init.

## Pack, sign and inspect — locally

```sh
axp pack
axp keygen --out ../hello-signing.key
axp release agent-extension.json --key ../hello-signing.key
axp check --format compact
axp verify agent-extension.json --artifact dist/package.tar.gz
```

Review the source, permissions and public artifact/update URLs first. `pack`
creates a deterministic tar.gz from an **explicit allowlist**, never the whole
repository by default. It does not update the manifest. `release` reuses the
existing release machinery: set/bump version, follow versions in URLs, compute
digests, stamp dates, sign and validate. It updates the manifest in place by
existing convention; `-o new-manifest.json` writes a separate file. An existing
`-o` destination now needs `--force`. Artifact/key destinations and symlinks
are refused even with force. Packing an existing archive likewise requires
`--force`; hardlinked outputs and directory collisions are always refused by pack.
`sign -o` refuses existing destinations; choose a new path or use
the explicit `sign --in-place` option to update the manifest.

For another version, edit the payload, `axp pack --force`, then
`axp release agent-extension.json --bump patch --key ../hello-signing.key`.
The local filename can stay `dist/package.tar.gz`; when uploading later, use
the filename in the manifest's versioned public URL.

On first signing, `sign`/`release` derive an absent `signing.public_key` from
the selected key. They never silently replace a declared, mismatching key;
rotation remains explicit (`--prev-key` and the existing signing workflow).
An unsigned release is still possible, with the existing warning, but `check`
will not call it publish-ready.

**Nothing has been published.** Upload the reviewed artifact and signed
manifest using your own release process; serve the publisher key directory
as described in [SIGNING.md](SIGNING.md). `check` cannot confirm remote hosting,
key-directory membership, ownership, host consent, or runtime behavior.

## `axp.toml`

This is local tooling configuration, not protocol metadata:

```toml
[project]
artifact = "dist/package.tar.gz"
signing_key = "../hello-signing.key" # PATH only, never paste a key here
files = ["install.sh", "uninstall.sh", "healthcheck.sh", "lifecycle.py", "payload"]
```

- Default config: `axp.toml` beside the manifest. `--config PATH` selects another
  file for `check`, `pack`, `sign`, or `release`.
- Config paths are relative to the config file, not the caller's directory.
  `~` expands in artifact/key defaults; no environment or shell expansion occurs.
- Explicit CLI options win: `pack --output` / repeated `--file`,
  `release --artifact` / `--key`, `sign --key`, and `check --artifact`.
  CLI artifact/output/key paths retain their usual current-directory meaning.
- Repeated `--artifact RUNTIME=PATH` retains existing per-runtime release mapping;
  a bare `--artifact PATH` supplies the default/canonical artifact. Config has one
  default artifact path; use CLI arguments for distinct runtime archives.
- `files` is a list of literal relative files/directories, not globs or commands.
  Directories are recursive. Missing entries fail instead of being skipped.
- Unknown sections/options fail with a message. There are deliberately no build,
  publish, shell, or lifecycle command configuration hooks.
- Python 3.11+ uses `tomllib`; Python 3.10 installs the conditional `tomli` dependency.

Pack refuses symlinks, hardlinked/special files, traversal/absolute archive
paths, local configuration, common secret filenames (`.env*`, private key
extensions, credential directories), PEM private-key material, and the configured
signing key regardless of its filename. Outputs cannot also be package inputs.
Checks inspect tar.gz/ZIP without extraction and reject duplicate entries, links,
special files, unsafe paths and file-as-directory ancestor conflicts. Truncated or
undecodable archives produce `AXP_ARCHIVE_INVALID`, including unsupported ZIP
compression. Limits are 10,000 entries / 128 MiB unpacked.
These are conservative packaging guards, **not an exhaustive secret scanner**:
review every allowlisted file, especially arbitrary tokens embedded in source.
Use an external packer for unsupported layouts, then review/check the artifact;
no unsafe bypass flag is provided.

## Honest readiness and stable diagnostics

`validate` remains a structural validator, with its existing default output and
exit codes. Opt in to `validate --format compact` or `--format json` for a
structured report. `check [agent-extension.json]` defaults to explanatory text;
it also supports `--format compact|json`.

Reports have `status`, `structurally_valid`, `diagnostics`, and (when valid) a
`summary`. Status values:

- `invalid`: unreadable/malformed input or a structurally invalid manifest.
- `structurally_valid`: **validate only**; no artifact/readiness claim.
- `draft`: valid manifest, but one or more offline readiness checks fail or cannot
  be completed. Fresh scaffolds intentionally have placeholder digests and no signature.
- `publish_ready`: all implemented **local static** checks passed. Not runtime
  certification, a security audit, or permission to publish automatically.

`check` returns 0 only for `publish_ready`; otherwise 1. CLI syntax errors retain
exit 2. `validate` returns 0 for structural validity, even for a draft.

Each diagnostic has stable `code`, `field`, `message`, and `remedy` strings.
Automate against codes/fields, not English message text. Check reports cover:

| Codes | Meaning / next step |
| --- | --- |
| `AXP_INPUT_INVALID`, `AXP_MANIFEST_INVALID` | Fix input/config/manifest at the reported field |
| `AXP_PLACEHOLDER` | Replace zero digests or reserved example domains |
| `AXP_FILE_MISSING`, `AXP_FILE_UNSAFE` | Supply safe local lifecycle/component files |
| `AXP_ARTIFACT_MISSING` | Pack or supply local artifacts |
| `AXP_DIGEST_MISMATCH` | Release hashes do not match supplied archive bytes |
| `AXP_ARCHIVE_CONTENT`, `AXP_CONTENT_MISMATCH` | Declared file is missing or differs from local source |
| `AXP_ARCHIVE_INVALID`, `AXP_ARCHIVE_UNSAFE` | Correct archive format, layout or secret content |
| `AXP_UNSIGNED`, `AXP_SIGNATURE_INVALID` | Sign/re-sign with the declared key |
| `AXP_RELEASE_EXPIRED`, `AXP_RELEASE_TIMEZONE_MISSING` | Renew release dates/signature or supply an explicit UTC offset |
| `AXP_RUNTIME_UNSUPPORTED`, `AXP_RUNTIME_UNCHECKED`, `AXP_DELIVERY_UNCHECKED` | Review runtime/delivery support separately |

`check --runtime hermes --runtime posix` requires a declared match. The bundled
runtime names are `posix`, `hermes`, `openclaw`, `claude-code`; this checks names,
not installed versions/platforms. Use `axp target` for host-specific selection.
Every distinct canonical and target archive is inspected, even when every target
overrides the canonical artifact, not just the selected runtime. Non-archive
methods and unrecognized runtime names remain draft rather than being silently
certified. Local references include lifecycle hooks, component `path`, relative
commands, and the first script argument of direct Python/shell/Node invocations.
Arbitrary shell text is never interpreted. No scripts or dependency checks run;
signature verification may use the existing fixed OpenSSL backend when the
optional `cryptography` dependency is unavailable.
